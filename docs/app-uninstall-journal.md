# 卸载记录、共享准入与重启对账

2026-10-23：已实现 `uninstall_journal.rs`、独立历史快照和 SQLite v4 迁移。当前只有初始化/备份/启动对账/保留规则接入生产；创建卸载会话、提交意图、原生处理和结果串联仍没有生产调用方，没有新增卸载或恢复 IPC/界面。它为 [完整 App 包处理](app-uninstall-target.md) 保存证据，不提供运行条件、确认或处理许可。

## 独立的单 App 记录

当前一份 [卸载计划](app-uninstall-plan.md) 对应一个完整 App 包和一个会话，不借用日志普通文件的扫描候选、确认、收据或记录类型。包外关联数据固定保留，多 App 编排尚未接入。

`uninstall_runs` 保存会话/唯一计划 ID、`appBundleTrash` 类型、状态、时间、不可变历史快照及 SHA-256、原因和 App 收据；`uninstall_events` 在同一事务追加状态变化，以数据库序号排序。它们没有对只读扫描/计划的级联外键，原清单或扫描回收不会删除卸载证据。

历史 `Archive` 绑定来源条目、完整包身份/主程序/清单、账户/主目录、固定 Mole 修订、范围和原期限。读取校验范围、版本、路径/祖先布局及摘要；支持同格式旧引擎修订的历史查看，不能据旧版本或已过期记录创建新意图。`Archive` 不能反序列化成 `Plan` 或活跃 `Session`，重启不恢复许可。摘要检测损坏，不是签名或防篡改认证。

## 意图与结果边界

所有写事务使用 `BEGIN IMMEDIATE` 并要求 SQLite `synchronous=FULL`；App 连接沿用 WAL、`fullfsync`、`checkpoint_fullfsync`。只有意图事务提交成功才返回成功，未来执行器必须在其后调用原生 API，并在最终门槛核对同一个会话、快照、原期限和当次条件。

| 转换 | 含义 |
| --- | --- |
| `pending → intent` | 已提交操作意图，尚无可靠完成结果；不可重复提交 |
| `pending → skipped/cancelled` | 开始前保留或取消，未调用 API |
| `intent → failed` | 原生目标/最终检查明确在 API 前拒绝，已知未调用 |
| `intent → moved` | 原生核心返回已核对结果，附原 App 身份与包清单一致的实际收据 |
| `intent → uncertain` | API 已尝试或意图未获可靠结算；有观察收据则保留，不自动重试 |

单 App 完成后直接结算批次；没有在途取消结算来丢弃 API 结果。已经有意图时不能以 `cancelled` 覆盖，完成后才到达的取消/停止也不能改写完成事实。结果允许在计划过期后写回，不能因过期而丢掉已发生的操作；过期只禁止新意图及最终处理准入。

已知未调用与未知结果分开记录。若操作后结果事务失败，原意图保留，下一次启动按待核实处理；不猜测目标位置，不从原文件消失推断成功，不补造收据或自动重试。

## 共享修改准入和容量

日志清理与 App 卸载分别记账，在各自 `BEGIN IMMEDIATE` 内共用 `execution_admission`：任一模块存在运行中或待核实结果，都拒绝新修改批次。独立连接竞争只能成功准入一个，读取/审阅仍可继续；这不是目标锁、主应用/辅助进程运行证明或完整任务控制。维护执行器接入时也必须加入相应准入，不能据此声称维护已实现。

两类记录合计最多 64 批、64 MiB 逻辑预留。App 历史快照最多 256 KiB，每个会话另预留 32 KiB，原因最多 1024 字节、收据最多 8192 字节。达到上限拒绝新批次，不丢弃恢复证据；这些不是 SQLite/WAL 实际大小或可用磁盘保证。

启动和保存设置沿用 7/30/90 天保留策略，回收不含修改的已结束取消/跳过/明确未调用记录；有收据、待核实或中断证据的记录继续保留。当前没有人工解除待核实、清除证据或产品恢复入口。

## 初始化、升级与中断

原 v1/v2/v3 库先通过 `VACUUM INTO` 保存 `moomole-before-v4-<uuid>.sqlite`，包含已提交 WAL；备份失败不迁移。缺失表与 v4 在一次事务中升级，失败回滚，原设置/历史/清理表及旧备份保留。新库直接建立 v4，v4 重启不重复备份，未来版本拒绝打开。旧版只支持 v3 的 App 无法直接打开 v4，需要保留新版及升级前备份。

生产初始化继续先取得 [数据目录占用权](instance-ownership.md)，在后台任务准入前对账：运行中 `pending → notStarted`，`intent → uncertain`，批次为 `interrupted`；已结束状态和收据保持。重复启动不重复追加事件。对账只修改数据库，不探测或操作目标。

worker 意外结束的 `stop` 只处理其自身仍运行的会话，遵循同一边界；它不能作为放弃正在执行的系统 API 的取消方法。实际执行 worker 仍需持有任务/更新/退出租约直到收集结果，这部分尚待串联。
