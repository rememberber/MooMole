# 执行收据定位与 Finder 取回

更新时间：2026-10-20。实现：`execution_location.rs`、`ExecutionLocation`。这是只读定位和系统交接，不是应用内恢复或自动放回。

## 用户流程

日志处理结果展开“实际移入位置”，或在历史逐项详情展开有收据的项目，可点击“在 Finder 中查看”。后端读取保存的收据、核对当前对象后请求 Finder 选中该文件。界面只说明已发送请求；用户仍需核对 Finder 中实际选择，不把 `open` 返回成功当成文件已被恢复。

需要取回时，在 Finder 核对“放回原处”是否可用。原位置已有文件时不要覆盖；Finder 不提供该操作、位置已被清空/移动/放回或权限受限时，应用如实提示，保留原始记录，不猜测另一个废纸篓路径，也不自动搜索、重试移动或标记“已恢复”。没有收据的待核实项不提供自动定位。

## 后端约束

- `reveal_execution_item` 只接受批次 ID 和项目 ID，不接收前端路径。数据库先核对不可变计划和逐项记录，再只允许 trash 方式的 moved/uncertain 且有实际收据的项目。
- 只定位收据中的确切文件，不枚举或扫描废纸篓。拒绝缺失、非当前账户、目录、链接、硬链接、未落地或非本地对象，以及设备/inode 不匹配；准备期间文件或祖先变化也拒绝。
- 普通清理使用的逐级打开目录不能直接用于废纸篓定位：本机允许打开确切文件，打开 `.Trash` 目录却返回 EPERM。本入口因此先逐级读取祖先元数据并拒绝链接，再以 NOFOLLOW/CLOEXEC/NONBLOCK 打开确切文件，返回前再次核对祖先、持有对象和具名对象。它不读取正文，不打开父目录来列举内容，不要求额外隐私授权；拒绝时保留错误，不放宽清理执行器的 AnchoredPath 约束。
- 请求 Finder 前再次核对，随后调用固定 `/usr/bin/open -R -- <收据路径>`，进程等待上限 5 秒。观察与 Finder 选择之间仍非原子，设备/inode 也不是永久身份认证；这里只辅助核对，不构成取回、覆盖或其他文件修改授权。
- 不改变 SQLite 记录或执行状态。Finder 手动放回是外部操作，应用只保留当时的处理事实；以后旧位置无法定位不等于能够证明已经恢复。没有新增系统权限、恢复 IPC 或 Shell 输入。

## 验证

普通 Rust 测试只操作新建临时文件：正确收据可准备且正文/记录不变，错误项目、无收据、未知/未开始状态拒绝；原对象移走、同名替换、文件/祖先链接、目录、硬链接和准备后内容变化拒绝。浏览器验证结果和历史两个入口，只传批次/项目 ID，定位失败仍保留处理结果，成功不重复执行或改成已恢复。

本机 Finder 联验使用单个新建临时 HOME 日志。正式日志循环、fixture 正面规则和真实 Foundation Trash 生成实际收据，SQLite 原记录读取后交给同一个定位函数。首次逐级打开 `.Trash` 的定位被拒绝，按独立保存的确切收据核对设备/inode 后无覆盖取回测试文件；改为上面的只读定位后成功。

随后原生 Finder 选中该唯一测试日志，“文件”菜单提供“放回原处”；实际点击后，测试核对原路径恢复、废纸篓收据位置消失、设备/inode 及正文一致，三个自建文件都在，SQLite 记录完全未改写，旧收据定位明确失败。此次用了 29.76 秒；没有操作其他废纸篓项目，没有向用户数据库写入模拟记录。

交互联验需操作 Finder，正常测试默认忽略；只在能够完成系统交互时运行：

```bash
node scripts/cargo.mjs test --locked log_cleanup::tests::finder_put_back_uses_exact_native_receipt_without_rewriting_history -- --ignored --exact --nocapture
```

测试会先保存确切收据和打印临时根/唯一文件名，180 秒未观察到放回则只对自己的测试文件按实际收据取回，失败时保留证据；原位置冲突不会覆盖。普通非交互原生回归应显式跳过此项：

```bash
node scripts/cargo.mjs test --locked log_cleanup -- --ignored --nocapture --skip finder_put_back
```

该联验覆盖当前机器普通文件的系统手动放回，不代表发布 App/TCC 身份、其他 macOS/架构、Finder 冲突选择、废纸篓被清空或跨卷已验收。完整应用内恢复仍是独立功能与授权流程。
