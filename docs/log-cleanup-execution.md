# 受限日志确认与执行

更新时间：2026-10-24。受限按次占用授权与普通账户废纸篓执行已在实际 arm64 ad-hoc App 完成正常链路：本人确认两份自建日志、真实规则、实际收据和 Finder 两种取回方式均通过。授权取消/拒绝、执行中取消/退出/强杀、权限/冲突/卷及安装后验收仍未完成；完整 clean、关联数据卸载、目录处理和应用内恢复仍未开放。实际证据见 [授权与恢复](cleanup-authorization-probe.md#实际修复版真实移入与-finder-取回)。

## 用户流程

在清理预览中选择项目、保存审阅计划，点击“复查 Mole 规则”。仅当来源明确的用户日志普通文件同时满足当前路径、模块、占用、权限、保护和原生准备条件时，才生成短期确认。任何未知或不支持范围保留，不把只读准备等同于许可。

只有占用仍为 unknown、其余上述条件均成立时，可生成**需要当次授权检查**的条件确认，unknown 不计为通过。“查看授权后移入范围”仍不触发授权；用户核对清单并勾选、点击“授权检查并移入废纸篓”才调用现有日志 worker。系统授权仅用于固定只读占用查询，之后重新运行 Mole 规则，满足当前条件才由普通用户执行器处理；失败或过期的文件保留。原 PID 1 诊断不是此许可。

“查看移入废纸篓范围”展示后端固定的文件清单、大小、其余保留数量及影响。勾选“已核对所列日志及处理影响”后才能提交。移入废纸篓不立即释放空间；当前不提供应用内恢复。确认过期、返回复查、取消、失败均不自动重试。

执行时可“停止后续项目”，等待当前项目的实际结果。结果逐项显示已移入、保留、未修改、取消或待核实，实际收据可展开，完整记录保存在历史。关闭弹窗请求停止后续项，后台仍负责收集当前操作结果，不因页面消失丢弃收据。

## 后端约束

- `log_cleanup::Confirmations` 在内存保存不可变子计划，绑定整个 SQLite 源计划摘要、选中项、trash 方式和最长 30 秒有效期；最多 8 份，一次取用即消耗。重启不恢复授权，刷新或重新复查撤销旧确认。
- `execute_log_cleanup` 只收确认 ID 和请求 ID，不接收路径、前端判断或替换后的选择。后端核对持久源计划与有效期、首次说明确认；同一时间仅一个日志修改任务，并加入退出取消及安装升级的任务准入约束。
- 每项执行前调用正式 `rules::run`，重新读取保护、身份与权限，再用同一个准备函数绑定原生对象。不使用确认时的旧规则代替当次检查；未知、白名单或其他限制都保留。固定范围限当前 HOME 的单层用户日志及诊断报告普通文件，当前 UID、单链接、本地已物化；最多 20 项。
- 需要授权时，后台先创建并绑定执行会话，每批一次固定 root 只读观察，持有原任务/更新租约。每项仅将对应观察合入当次通过的日志规则，不覆盖已发现的 busy、白名单、失败或不支持。Guard 保留原生查询起始时间，在意图前和最终 API 调用前核对；达到 5 秒、取消或对象改变即拒绝，不用新接收时间续期。授权失败/取消记录逐项保留或取消；实际系统窗口仍须本人操作。
- 最新保护/首次说明/计划时间再次核对后，先提交 SQLite 意图，才做最终对象复核及 Foundation Trash 调用。最后复核拒绝时标记未修改；一旦调用 API，错误或证据不足均记待核实并停止后续，不虚报“未发生修改”。
- 检查前的名称、父目录或正文变化拒绝；最后检查和系统调用之间仍非原子操作。处理后核对返回对象身份、内容元数据、原范围和原路径消失；变化保留实际收据和待核实状态。没有取得全局锁，也不保证内容持续静止，详见 [并发边界](cleanup-concurrency.md)。
- 批次检查点预算 120 秒，不承诺强行中止正在发生的系统调用。取消只停止未开始项，已经发生的结果必须记录。已产生执行记录的计划不重放，需要重新扫描；不确定项不能自动重试。
- 不新增数据库 schema、Shell 修改入口、私有权限或特权 helper。SQLite 记录失败立即停止；遗留意图由现有启动对账标为待核实。记录层自身不提供文件操作权限。

## 后台跟踪与批次取消

日志请求进入后，主界面会跟踪执行记录；有进行中批次时显示紧凑状态提示，可直接前往历史。页面重载从 bootstrap 返回的进行中批次继续读取状态，不重新确认或执行。全局列表和已打开的运行详情按请求结束后 1.5 秒继续读取，不叠加同一观察器的请求；读取失败退避至最多 15 秒，保留上次证据并提示状态待确认，恢复后自动更新。停止观察不取消操作。

历史的运行详情可“停止后续项目”。新增 `cancel_log_cleanup` 只接受批次 ID；执行 Job 在正式记录创建后绑定一次批次，晚到、未知或旧批次不能停止下一次任务。这个入口只请求取消，不移动文件。请求成功时显示等待当前项的实际结果，不提前改写终态；请求失败可重新请求，仍以逐项记录为准。终态不显示取消入口，搜索和筛选在持续更新时保留。

迟到列表不会把已记录终态退回运行中，也不会减少已移入数量；较旧详情不会覆盖已有的更多事件。关闭详情只停止详情读取，全局仍观察；关闭原确认弹窗请求停止后续项；原生进程退出和强杀继续沿用取消/持久意图对账，不因跟踪功能自动续删或恢复。现有只读任务快照协议与这里的 SQLite 执行观察分别管理。

## 已验证与剩余验收

普通回归验证确认绑定、源计划变化、过期/时钟回退、撤销、一次使用、保护新增、占用未知、取消与拒绝重放。浏览器使用纯模拟执行回调验证两步确认、固定范围、错误消耗、过期禁止，以及执行中确认到期后取消仍显示已完成结果；不操作本机文件。

显式原生联验只使用新建临时 HOME 的日志文件：实际生产执行循环在 fixture 规则下分别完成两项移动及首项完成后取消；SQLite 实际收据写入救援报告后，按确切返回路径核对设备/inode 并取回所有自建文件，再核对原始内容与未选文件。正面规则是明确的 fixture，不描述为本机真实占用检查通过。

另一项联验在生成确认后向隔离 HOME 添加真实 Mole 白名单，再运行正式执行器和固定 Mole 规则：两项均保留、无原生收据、批次 noChanges。Mole 会在专用 HOME 的 Logs 下创建自己的日志目录，验收单独统计原始普通文件而不把该目录当多出一个用户文件。此前真实来源 ledger → 计划 → 规则 → 只读准备的本机结果仍为 activity=unknown，必须保留。

```bash
node scripts/cargo.mjs test --locked log_cleanup -- --ignored --nocapture --skip finder_put_back
```

最终门槛还重新读取目标及父目录的权限、ACL、卷状态及锁定属性；限制或未知拒绝，逐项原因说明返回计划复查，不自动解除限制。三类意图后权限收紧联验和五个强杀关口已通过：原生返回但尚无 SQLite 结果时重启保持 uncertain 且没有补造收据；已提交结果/终态保留。仅测试编译的检查点和独立救援报告用于取回自己的临时文件，不进入 release App，不给正常执行额外补成功或恢复能力。证据和边界见 [日志原生强杀矩阵](execution-crash-recovery.md)。

结果和历史现可通过保存的收据 ID 请求 Finder 定位，不接收前端路径，重新核对当前对象，失败保留原记录。本机一个自建普通日志的真实 Finder“放回原处”联验已通过，取回后旧收据位置失败、SQLite 不改写；没有开放应用内恢复。详见 [收据定位与 Finder 取回](execution-location.md)，交互测试与非交互原生回归分开运行。

所有实际移动只针对自建测试文件，成功后按实际收据完整取回；失败保留临时根、SQLite 和收据报告，不枚举或清空用户废纸篓。上述关口不代替发布 App/WebView IPC 与 TCC 身份下拒绝、只读卷、系统原生调用内部强杀/断电、Finder 冲突选择、跨卷或其他架构机器验收。下一关口优先完成这些限定范围验收，再推进其他 Mole 核心流程；不继续扩张应用列表长尾规则。

## 当前普通账户的执行可达性（2026-10-21）

固定源码 `lib/core/file_ops.sh:_mole_complete_lsof_mode` 先尝试读取 PID 1 的 root 进程字段，证明完整视图后才允许空匹配成为 noOpenHandles。当前适配批次清除继承的视图结论并设置 `MOLE_TEST_NO_AUTH=1`，不走 sudo 授权回退。本机普通账户的实际结果是 unknown，因此当前真实 App 不应显示可执行确认；构建、fixture 正面执行或新增原生故障测试都不能改变这一事实。

后续需要验证无付费开发者证书条件下的受限按次系统授权、调用方/来源/协议核对及文件隐私权限边界，不能简单删除完整视图要求、启动整个 App 为 root、传密码或开放通用 Shell 来完成验收。此项继续阻止日志功能的发布完成声明；状态持续采集等不修改文件的核心流程可同步推进。
