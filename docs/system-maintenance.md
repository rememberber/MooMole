# 系统维护：项目说明与执行边界

2026-10-21。当前提供固定 Mole 版本的维护项目说明，以及两项设置的本机只读观察与项目级保护检查；尚未连接修改计划或执行。这里的“预览”是作用与影响预览，不是待执行对象列表，也不表示本机需要维护。

## 当前可查看内容

- 侧栏“系统维护”可浏览 Mole 1.59.1 的全部 19 项目录，顶部搜索名称、用途、影响、权限或原始 action ID。
- 默认仅显示项目名称、用途与操作性质；展开后查看范围、执行前条件、权限、可能影响、恢复限制。技术来源按需展开，不重复页面标题和装饰性路径。
- 无论是否能使用引擎，都不报告本机健康结论。引擎不可用或版本/提交不匹配时，额外注明仅为固定版本功能参考。
- 文件系统验证保留上游默认禁用；启动代理、登录项检查说明其只报告问题。删除旧记录、重置设置与刷新服务分别标明，不能笼统称为无风险优化。
- 顶部“检查本机设置”仅按需读取 Finder 两项记录设置和四项 App Nap/映像验证覆盖设置。逐键展示启用、未启用或未知；管理策略标记及维护任务跳过规则单独展示。其余 17 项继续明确未检查，不因这两项完成而推断可执行。
- 检查结果只代表所标时间；重试失败保留旧结果并注明本次未更新。离开页面不接收迟到结果、不自动重新检查。界面不提供中止系统读取的承诺或修改按钮。

## 两项只读检查的语义

`prevent_network_dsstore` 对应 `DSDontWriteNetworkStores`、`DSDontWriteUSBStores`；`legacy_overrides_audit` 对应全局 `NSAppSleepDisabled` 及 DiskImages 的 `skip-verify`、`skip-verify-locked`、`skip-verify-remote`。Rust 使用 CFPreferences 读取有效值及 forced 标记，不调用 defaults 命令、不解析终端文案、不调用 synchronize/set/delete，不枚举整个偏好域或返回无关值。

仅布尔值、0/1 整数和明确支持的有限字符串可转换；缺失和读取不可用无法通过该 API 可靠区分，因此 NULL 一律未知。浮点、异常字符串、嵌入 NUL 等也未知。系统策略管理的设置应保持现状；部分覆盖值已启用而其他值未知时，保留已经观察到的启用证据。即使两个 Finder 键都启用，“无须重复设置”也只针对这两个键，不能视为整机正常或取得维护许可。

维护规则只读适配 `load_whitelist optimize` 的来源优先级：先读 `~/.config/mole/whitelist_optimize`，物理缺失时才读 `whitelist_checks`，两者均缺失才使用固定版本的空默认列表；新文件为空不回退旧文件。只判断两项 action ID 的精确命中，glob 不用于任务名匹配。**不调用上游 load_whitelist**，因为其旧文件兼容分支会自动保存新文件。路径/glob 保护、清理白名单和客户端保护目录不在本轮映射为“通过”。

规则文件限制 64 KiB / 256 条非注释规则，要求完整 UTF-8、无 NUL 且最后一行有换行；无末尾换行虽然上游可能忽略该行，本客户端保守标为未知。通过描述符绑定验证目录链、文件身份、内容时间与本地物化状态；链接、硬链接、非普通文件、非本地/未物化路径、权限异常或变化均未知，不创建目录或迁移配置。读取相对于已持有的父目录打开，只读文件描述符在读取前后核对。

单 worker、单并发；原生 IPC 5 秒等待，内部约 4 秒后不再发起新设置读取，前端 7 秒等待。系统调用本身不能保证强制中断，超时后实际 worker 继续持有并发槽和安装操作租约，直到真实返回；不因为界面超时就重复启动 worker 或宣称取消成功。无轮询、无自动重试、无数据库保存或维护任务历史记录。前端核对协议、源码基线、两项目/六键完整性、时间及保护/状态一致性；过期响应或迟到观察不替换当前结果。

## 来源与更新约束

`src/lib/maintenance-catalog.json` 是中文解释元数据，固定 `1.59.1` / `ba3a0f57f78e4c22818fda701219cc3dd4d6953f`。19 个 action 与 handler 按 `lib/optimize/catalog.sh` 的注册顺序逐项对应；说明审阅了 `tasks.sh` 与 `maintenance.sh`，并区分上游条件与客户端未来需补齐的保护。

引擎准备脚本在源码归档解包后、编译和资源安装前，检查版本、固定提交基线、catalog/tasks/maintenance/whitelist/base 五个文件的 SHA-256，以及完整 action/handler 对应。变动会失败并要求重新审阅。此检查只读文件，不 source Shell，不启动 optimize 或 dry-run，不索取授权。可单独运行：

```sh
npm run test:maintenance
node scripts/maintenance-catalog.mjs .cache/mole-source
```

浏览说明、展开和搜索不会触发 CLI；仅用户明确点击检查才调用无参数 `inspect_maintenance`，后端固定范围、要求首次说明已确认并复核引擎完整性/版本，拒绝退出或安装交接中的请求。已有 App 启动时的系统快照属于原有状态流程，不能作为维护适用性证据。

## 后续开发顺序

1. 在两项设置观察基础上补齐对应路径保护、写入权限及可恢复原值，再扩展少量实际任务；不解析终端文案生成删除目标。
2. 继续适配维护自己的路径保护与其他任务有效规则，不能用清理白名单或客户端保护列表代替。DNS 还需考虑上游旧 `system_maintenance` 规则兼容，本轮不判断 DNS。
3. 为具体项目定义选择范围、证据时效、执行前身份与活动占用复核、按项结果及取消边界；未知不放行。
4. 修改设置需记录原值，删除数据需备份和恢复设计；数据库需处理 WAL/SHM 及服务活动；重建索引启动后系统仍可能继续工作。
5. 免费分发下逐项验证授权路线，不依赖付费 Developer ID 常驻 helper，不关闭 Gatekeeper 或删除文件安全属性。

当前不提供“一键优化”，也不把 `optimize --dry-run` 的文案当作结构化执行计划。上游对目录的自动执行标记不是本机可安全执行的证据。未作任何维护修改、权限请求或性能改善承诺。
