# 应用详情检查耗时与超时

2026-10-19。保持 Mole 清单绑定、原身份复核和保护语义。当前没有提高 5 秒等待期限，也不把超时或范围不完整转换成通过。

## 超时处理

每个请求独立保存静态阶段编号与停止标记。阶段覆盖工作器排队、固定规则、主身份、后台条件、嵌入组件、关联位置、扩展数据、常用安装根、本地卷、收据、共享副本、主运行状态、返回前复核和规则附加。超时显示当时所处的环节，例如「应用状态读取超时（核对安装收据），结果无法确认；请稍后重试」。这说明当时正在做什么，不认证根因或耗时来源。

5 秒停止等待时仅设置当前请求的停止标记。排队工作器运行时先检查停止；已开始的工作器在后续各阶段入口检查停止，撤回整份观察，不发布未复核或较早结果。已打开句柄按原所有权释放，不继续后续阶段的查询。当前阶段可能包含多个文件/系统查询，只能在它返回后的检查点退出；不会强杀线程、AppKit 调用或已启动的收据进程，也不改变进程组清理与回收规则。

工作器名额仍在真实闭包内持有，包括停止等待后仍在排队或阻塞的时间；只有闭包实际返回或异常退出才释放。不能因界面已经显示超时而再启动无限量工作器。两个请求的阶段和停止标记独立；完成与期限同时就绪时优先接收已完成结果。面板关闭后的迟到响应仍由前端代次规则忽略，当前改动不是新增 IPC 取消接口。

没有增加页面或调试字段。正式程序只保存阶段编号与停止标记，不记录分段时间、路径、Bundle ID 或请求日志，不写 SQLite、用户设置或任务历史。当前应用协议为 v27；阶段提示本身不改变成功返回的来源范围或保护要求。

## 显式只读测量

只有测试构建编译分段计时模块。下面两个诊断默认忽略，需要本机安装对应应用，使用当前 HOME、固定引擎资源及系统发现来源；不清除系统缓存、改变权限、退出目标应用或制造数据。

```sh
node scripts/cargo.mjs test --release --locked installed_code_read_only_profile -- --ignored --nocapture
node scripts/cargo.mjs test --release --locked installed_mootool_read_only_profile -- --ignored --nocapture
```

每个命令从实际 Mole --list 的成功结果，经同一任务缓存方法绑定条目名称/标识和前 65 个候选，随后在真实阻塞线程上连续执行三次同一 inspect_worker；共享运行时供收据子进程使用。测量包含规则加载、系统登记/运行与完整元数据流程，不使用前端伪造路径。它不通过界面发请求，不包含图标并发、SQLite 最后保护附加或 WebView 往返，不能替代原生验收。首次是新测试进程中的首次检查，不代表清空 OS 缓存后的冷机。

成功测量只输出静态阶段名、耗时、候选总数和范围状态，不输出应用路径、标识或列表内容；不保存报告文件。最多 32 条计时记录，线程内捕获，仅包围当前显式诊断；其他测试和正式程序不启用计时。受控工作器测试使用信号通道触发期限和解除阻塞，不以真实文件权限或慢磁盘制造故障。

第六十七阶段（协议 v20、六类基础名称位置）的本机 arm64/macOS 27.0.1 优化测试构建，两个命令各在独立新进程运行，实际清单均为 58 个候选，测得工作器加排队时间如下。每轮关联位置为 observed，嵌入组件、共享安装和收据仍为 partial；耗时结束不等于完整发现。

| 目标 | 第一次 | 第二次 | 第三次 |
| --- | --- | --- | --- |
| Code | 1627ms | 1602ms | 1590ms |
| MooTool | 1710ms | 1645ms | 1661ms |

收据初查为 1510–1551ms，处于原有 1500ms 检查点预算附近；该预算不能硬截断子进程和当前调用。保护规则约 26–41ms；Code 的名称所在关联位置阶段约 1–2ms。本轮这些测量未出现 5 秒超时，不能据此归因上一轮的首次超时，也未提高正式等待期限。新包原生首次检查与重查记录见开发日志。

## 已知限制与后续

第六十六阶段 Code 与 MooTool 的原生首次检查曾超时，重查恢复；第六十七阶段的分段测量未复现。分段测量与原生结果记录在开发日志；没有复现时，不将收据的正常预算耗时认定为首次超时根因，也不把复测成功称为性能问题已经修复。

第六十八阶段原生检查 Code 时再次超时，首次和首次重试都报告「核对本地卷」。14:51:06 的只读线程采样在 1 秒内取得 91 个相同阻塞栈：inspect_worker → begin_volumes → volume_level → open → openat/__openat。已带 O_NONBLOCK 的目录打开仍可能等待内核；该证据说明本地卷发现确有阻塞，未取得调用参数，不能认证具体卷/路径或系统等待原因。未采集用户内容，原始线程/文件描述符诊断不放入仓库或发布物。

结合挂载快照中存在的本地 nobrowse 系统卷，客户端现在在打开和子项元数据查询前排除 MNT_DONTBROWSE 挂载，并把范围标为 unsupportedVolume/partial，仍保留真实工作器占用与 5 秒等待。它是有依据的支持范围收紧，不是硬中断 I/O，也不保证普通本地卷不会阻塞；修正后原生结果记录在第六十八阶段开发日志。

仍需取得实际超时时的阶段和系统调用证据，覆盖 GUI 冷启动、图标并发、权限等待、慢本地卷/外接卷、系统登记服务、收据进程退出与清理的组合。各阶段的独立预算相加并不是总请求的硬上限，检查点也不能限制单次内核 I/O。后续若调整预算或并发，须保留范围不完整、身份撤回与默认保留规则，并建立可重复的机器/系统基线。
