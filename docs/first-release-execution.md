# 首个可用版本：三条真实执行闭环

2026-10-23，用户明确要求：**首个对外可用版本必须包含真正的清理、应用卸载和系统维护执行。** 此文件落实首次可用发布的门槛，不把现有只读基础或内部实验当作可发布功能。

## 完成标准

三个模块都必须在清楚声明的支持对象上，经实际打包 App 完成用户选择、影响说明、确认、当次复核、真实操作和逐项结果。正常对象至少有实际完成的正面流程，保护、未知、权限不足和不支持对象则有明确保留/跳过原因；不能用全部跳过、本来无须变更或 fixture 通过充当真实执行。

取消保留已发生的结果，终态和中断均可从历史核对，重启不自动重放修改。恢复方式按操作明确：废纸篓使用真实收据和已验证的 Finder 恢复边界；偏好设置按原类型/域和冲突条件恢复；缓存刷新解释重建行为，不承诺恢复原缓存或必然提速。未知结果不自动重复执行。

首批支持范围可以受限，但不以单个自建测试文件替代具有日常用途的清理支持，不以显示应用清单替代卸载，不以展示 19 项维护说明替代维护。完整 1.0 路线图继续保留，范围变化必须明确记录，不能借“测试版”隐去用户要求。

## 当前真实缺口

| 模块 | 已有可复用基础 | 距离真实交付的主要缺口 |
| --- | --- | --- |
| 清理 | Mole 结构化候选、审阅/保护/规则复核、短期一次确认、限定日志原生循环、意图/结果记录及取消接回 | 普通账户完整占用视图受限；当次授权路线、实际发布 App 的正常处理/拒绝/退出与中断验收未完成；日志之外的缓存或目录尚无可直接复用的执行资格 |
| 卸载 | 独立计划、当次复核、一次确认、原生处理/FULL 记录、取消/接回及桌面界面；自建 GUI App 在实际包的正常移入、历史、重启与 Finder 取回已验证 | 实际 App 的失败/取消/退出/中断、权限和冲突矩阵仍待完成；固定范围未发现不等于排除所有后台注册或管理器 |
| 维护 | 固定 Mole 19 项目录；首批 Quick Look 已接固定选择/规则保护、一次确认、系统命令/FULL 记录、worker 排他、取消、历史接回与未知人工核查；实际 App 已由用户明确触发两步，均零退出，历史与正常退出/重启保持 | 执行中取消/退出/中断及缓存重建体验仍待验收；目录删除和偏好写入继续保留 |

首发的共用能力是确认、任务排他、意图/收据、取消、退出及历史接回。对象和规则必须分别建模；不能把日志普通文件的条件直接扩成目录卸载，不能把只读维护审阅直接改为 `canExecute=true`，也不提供任意路径/域/命令的通用修改接口。

## 第一关：清理权限与占用视图

现有 `moomole-review-rules.sh` 显式设置 `MOLE_TEST_NO_AUTH=1` 并清除继承的 `_MOLE_COMPLETE_LSOF_MODE`。固定 Mole `lib/core/file_ops.sh:_mole_complete_lsof_mode` 要求证明完整进程视图，普通检查不足时才尝试已有授权的 `sudo -n`；当前适配禁用该回退。本机读到 unknown 的记录不是测试噪声，更不是增加模拟正面结果就能解决的问题。

受限按次系统授权已限定为固定、有界的只读占用检查，并接入条件确认及普通用户日志执行器。下一关是实际 ad-hoc App 的正常处理、拒绝、取消和故障验收；代码及内部 fixture 不代表已取得实际用户授权或已有可发布闭环。没有引入常驻 helper。

固定只读候选的机制取舍、实现与实测限制见 [清理授权探针](cleanup-authorization-probe.md)。实际 ad-hoc App 已在本人操作后读到 root/PID 1 字段，定位并修复客户端遗漏 lsof 必带 f 字段的误拒绝；修正版完整原生正面验收待用户方便时继续。没有据系统确认或字段存在本身开放清理；PID 1 的证明也不能代替所选对象的当次占用检查。

- 核对调用方/检查程序的来源、版本和身份，固定请求协议和操作白名单，不接收通用 Shell、程序路径或任意参数。
- 请求绑定当次计划、明确对象身份、实际用户及有限有效期；结果不可跨计划、对象替换或重启重放。占用复核和最终处理之间的竞争边界仍须保留，不宣称授权消除竞态。
- 验证授权取消/拒绝、检查失败/超时、进程可见性不足和隐私权限受限。root 不等于绕过 TCC，不能据授权成功就产生 noOpenHandles。
- 不以 root 启动整个 App，不在前端收集或保存管理员密码，不依赖尚未验证的付费 Developer ID 身份或常驻 helper。
- 技术结论须能在实际打包 App 和自建目标上复验，未经实机验收不宣布可发布；运行时条件不满足则保留项目。系统授权及实际处理须由用户在具体程序、固定范围和影响可审阅后明确触发，开发范围确认不作为代理操作真实个人数据或系统设置的授权。

现已接回限定日志循环，每批一次 root 只读检查，逐项重新运行 Mole 规则，并在最终普通用户 API 前核对原生观察。接下来验收真实规则/白名单、实际废纸篓收据、取消/退出和重启结果，再确定有日常用途的首批日志/可重建缓存支持范围。目录、共享数据、数据库和系统范围分别验收，不能沿用普通文件资格直接开放。

实际修复版 App 已由本人提交两份自建日志并进行系统确认，结果为两项占用未知而保留、无意图/收据，原文件完整。已据此补充视图/精确查询的有限诊断及具体保留原因；尚未取得真实清理成功证据，不能把该全保留批次计为本关完成。详见 [实际授权记录](cleanup-authorization-probe.md#实际所选日志首次授权与诊断补充2026-10-24)。

## 第二关：首批普通应用卸载

从身份明确的普通 App 包开始，形成独立卸载计划：固定本次应用对象、包身份、选中项、方式、影响和有效期。关联缓存/日志及个人数据分别列出；个人数据默认保留，归属、共享或保护证据不足的关联项不参与处理，也不能因此声称已完整删除所有残留。

已完成 [独立后端计划基础](app-uninstall-plan.md)：从保留的成功清单绑定条目，固定 Applications 直接子 App 的实际身份文件、主程序与完整包清单，复核不续期，撤下或新检查后旧结果不复活。框架链接仅记录字面值、不跟随，包外关联数据全部保留；只读计划始终不可执行，前端未接。[原生处理核心](app-uninstall-target.md) 的自建包实际移入/收据/取回测试及 [独立记录层](app-uninstall-journal.md) 的事务/共享准入/迁移/启动对账测试分别通过。后续执行器串联情况见下文；下一步接前端和历史，不继续扩展厂商长尾。

后续 [运行检查与短期确认草稿](app-uninstall-runtime.md) 已接只读后端入口，按实际可执行路径识别主程序/包内辅助进程，绑定原始新鲜度、完整计划与保护上下文。脚本、未知/变化和已发现进程不产生草稿；该观察不含包外服务/管理归属，也不提供最终处理许可。后续补充的固定范围管理检查和执行器见下文，不以确认或未发现进程替代真实卸载门槛。

草稿现已叠加 [普通 App 固定范围检查](app-uninstall-support.md)：包内后台/特权声明、标准 Launch 配置/辅助工具与默认 Caskroom 的相关线索均保留，未知或变化撤回。它不覆盖所有后台注册和安装管理器；明确提交后的当次复核与记录串联见下文，用户流程及实际 App 证据继续待完成。

[专属执行器](app-uninstall-execution.md) 已接后端明确提交、当次全部门槛、意图/原生调用/收据与请求 ID 接回，v2 确认要求普通 App 范围的明确确认。自建 App 的实际 Mole 清单 → 系统废纸篓 → 记录 → 确切无覆盖取回通过；这不是前端或实际打包 App 的用户流程验收，不能勾选本关。下一步接前端和历史，再验证真实 App 正常/取消/退出/重启及恢复边界。

后续 [界面和实际 App 正常路径](app-uninstall-interface.md) 已补：对唯一自建 GUI App 验证运行中保留、退出后重新检查、明确勾选、真实 moved/收据及历史重开，Finder 手动无覆盖移动取回也通过。它补齐了正常 UI 的证据，完整取消/中断/拒绝/权限与冲突矩阵仍待验收，不能单凭正常路径勾选完整卸载关口。

执行前重新核对目标 App 包、当前运行/后台状态、客户端自身/系统组件/保护目录和固定 Mole 的相应规则。提供用户明确退出/取消操作，不自动强杀、关闭服务或启动官方卸载器。需要官方卸载器、特殊安装/后台管理或权限路线尚未支持的应用，直接说明原因和下一步，不用新增全部厂商特例来阻塞普通范围开发。

完整 App 包实际移入废纸篓，记录系统返回收据与核对结果；取消只停止后续项，记录部分失败/待核实状态，按验证过的方式定位和恢复。使用自建 App 包进行初轮原生验证，再验收声明支持的受控应用与权限场景；不通过移除开发者真实日用应用来制造测试结果。

## 第三关：固定维护任务执行

首批已选定固定 Mole `cache_refresh` 中的 Quick Look 缩略图缓存和生成器刷新，两步分别建模；不含该 handler 的显式目录删除，也不把整项 Finder 缓存处理声明完成。固定选择、一次确认、当次规则/保护、实际命令/worker、[逐步记录](maintenance-refresh-journal.md) 与 [桌面流程](maintenance-execution.md) 已接通；实际 App 已由用户确认并完成两步真实刷新，历史和正常重启保持同一结果、无重放。下一步完成执行中取消/退出/中断及重建验收，不能以测试替身充当这些证据。

选择该路线的依据及后续任务边界：

- 已有偏好类任务：沿用观察/保护基础，先解决真实明确域的原始值/缺失证据、持久意图、类型精确读回、跨进程恢复与并发边界；不能直接把实验 UUID 域的 writer 换成 Apple 域。
- 缓存刷新等固定任务：首批 Quick Look 无需管理员权限，按原 handler 的维护白名单及客户端保护建模，核对命令实际结果和重建影响。DNS 等需要授权的任务另行验证，不把偏好备份实验视为通用执行器。

UI 只提交任务/确认 ID 和所选固定项目，后端决定操作与参数。执行前条件不满足则保留；已启动的服务操作如何收集结果、后续项如何取消，必须按任务语义分别说明。偏好变化、缓存刷新、服务重启的成功与恢复标准不能混用，不承诺统一回滚或没有依据的性能提升。

## 发布关口与工作优先级

1. 完成清理权限技术验证和实际 App 的首批清理闭环。
2. 交付普通应用的首批真实卸载；同一阶段复用已验收的确认/记录基础，不扩展厂商长尾来替代执行。
3. 冻结并交付首批固定维护任务，完成对应失败/取消/恢复或重建验收。
4. 三条执行分别具备正常与失败证据后，执行跨模块排他、退出、重启、更新交接和真实支持环境回归。
5. 从固定提交生成免费 ad-hoc DMG，完成下载/系统确认/安装/升级及源码、许可证、隐私、已知限制等发布材料后，才发布首个对外可用版本。

影响现有正确性的修复仍可进行；其余只读指标、最近目录等便利功能和厂商专属位置扩展暂不继续占据执行主线。没有因本次要求降低保护、增加付费签名条件或默认允许修改个人文件。已有分阶段证据见 [开发记录](development.md)，完整功能范围与其余发布条件见 [发布路线图](release-roadmap.md)。
