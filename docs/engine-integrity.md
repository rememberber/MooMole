# 引擎隔离构建、原子发布与完整性检查

2026-10-15。适用于固定 Mole `1.59.1` / `ba3a0f57f78e4c22818fda701219cc3dd4d6953f`。这是开发构建流程，不是 App 内引擎更新器。

## 准备流程

1. 获取 `src-tauri/resources/.mole-prepare-lock` 排他锁，写入本次 PID 与开始时间。并发准备直接拒绝，不删除其他进程的锁。
2. 在 `.cache/mole-build-*` 创建独立工作区，在资源目录创建同卷 `.mole-stage-*`；旧 `resources/mole` 保持原位。
3. 获取固定提交并检查 HEAD/已跟踪文件；通过 `git archive` 导出固定树到独立工作区，避免把 Git 缓存中的未跟踪文件或旧二进制带入构建。
4. 从导出的源码复制 `mole`、`mo`、`bin`、`lib`、许可证与商标政策；从本仓库复制两个只读适配脚本。使用 `go build -mod=readonly -buildvcs=false -trimpath` 构建分析与状态二进制，明确指定 Darwin 和当前 arm64/amd64。
5. 从唯一 `VERSION` 赋值读取 CLI 版本，核对薄 Mach-O 架构及执行位，生成资源摘要与构建清单，再完整检查 staging。
6. 本机编译仅供构建使用的 `engine-install.c`。首次安装用 `RENAME_EXCL`，已有生成目录用 `renameatx_np(RENAME_SWAP)` 在同一父目录内交换；不使用“先移走旧目录，再复制新目录”的缺失窗口。不支持该原语的文件系统会拒绝，不退回非原子覆盖。
7. 交换后清理本次唯一 staging 中的旧生成目录，释放锁并清理本次工作区。不会扫描或清理个人缓存目录。

目标 `resources/mole` 明确是被替换的生成输出，不能存放人工源码修改；已有目标必须是物理目录，且其旧清单声明预期仓库与有效提交 ID。陌生目录/链接不自动覆盖。

准备失败发生在发布前时，旧目录不变。测试覆盖构建失败、校验失败和替换失败；原生交换已在实际开发卷以及临时 fixture 目录执行成功。这不是跨多个文件打开的事务快照：正在运行的开发进程仍可能跨交换看到不同世代而校验失败，应停止使用该资源目录的开发任务后准备。已打包 App 使用自己的资源副本；GUI 不调用本脚本。

## 离线、重试与中断

```bash
npm run engine:prepare
# 固定提交及所需 Go 模块已经在本机缓存时：
npm run engine:prepare -- --offline
npm run test:engine
```

离线模式跳过 Git fetch，禁止模块代理下载和在线 sumdb 查询，仍使用固定源码的 `go.mod` / `go.sum` 及只读模块构建。缺少固定提交、模块或工具链时失败，不能把半成品安装为引擎。它不提供工具链/模块的离线安装包。

普通异常路径会释放锁并删除本次临时输出。被强制终止或断电时，锁/临时目录可能保留；核对 `owner.json` 的进程及路径后再人工处理，脚本不凭 PID 过期猜测自动删锁。重命名完成但进程未报告成功的极端中断，应检查现有清单后重新准备，不把命令退出状态当作断电事务证明。原子可见性不等于断电持久性认证。

## 清单与运行检查

`UPSTREAM.json` schema 1 包含：

- 仓库、固定提交、CLI 版本、平台、架构。
- `cleanProtocol=2`、`rulesProtocol=4` 和 `build.recipeVersion=1`。
- 实际 Go 版本、构建 GOOS/GOARCH；不保存临时绝对路径或完整进程环境。
- 每个相对资源路径的字节数、SHA-256 和执行位；清单自身不递归计算摘要。

准备端和 Rust 启动端都验证清单。App 启动与启动已知引擎任务前检查资源集、大小、摘要、执行位、协议组合、CLI 版本及二进制架构；旧清单、缺失/额外文件、同长度改动、链接、共享硬链接、特殊文件或错误架构不会显示为可用引擎。

检查限制：清单 1 MiB，最多 512 个文件、1000 个目录项、64 层目录，单文件 64 MiB，总声明资源 128 MiB。Rust 按块计算摘要，不把完整二进制读入一个缓冲区。当前真实构建为 62 份资源，约 14 MiB。

资源摘要用于发现缺失、混版和损坏，**不是发布者签名**；能同时改写清单与资源的攻击者不在该校验的认证能力内。后续免费 DMG 的下载校验、自有更新签名、来源约束和 App 签名验证仍各自需要完成。

## 发布签名边界

本次 debug App 中包内资源和清单检查通过。将来 ad-hoc 签名可能改变 Mach-O 字节，不能继续使用签名前的可执行文件摘要：发布流水线应先完成内嵌程序最终签名，再生成对应资源清单，最后签名/封装 App，并对最终产物重新校验。不得在已经签名的 App 中直接改清单后宣称签名仍有效。

此阶段未完成上述 release 签名顺序、Intel、干净机器或 DMG 安装验证；不需要购买 Apple 开发者账户。后续约束见 [distribution.md](distribution.md)。
