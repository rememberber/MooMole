# 清理与卸载的未知结果核查

清理或卸载在原生调用后失去可靠结果时，记录保持待核实并阻止新修改。此前界面提示到历史核查，却没有解除该阻塞的核查入口；不能把这种永久阻塞当作完整恢复体验。阶段 160 补齐独立核查记录，实际执行、逐项结果和收据不改写。

## 用户流程与边界

在“操作历史”的执行记录或卸载记录，打开确切批次，先核对原对象、废纸篓、收据及逐项结果。确认未知结果不会自动重试后，明确勾选并点“记录已核查”。这只保存本人已核查的确认，不说明原操作成功、文件已恢复或可以按原路径重做；取回仍按原 Finder 无覆盖边界处理。

阶段 162：返回 App 后，历史之外的工作区也提示未核查卸载的数量，并可直接打开确切记录。只读取已保存列表，不自动检查或提交卸载，也不自动勾选核查；关闭详情保留提示，明确核查后收起对应要求。运行中的状态提示优先，已核查或已知结果不重复要求核查。

保存后继续显示原来的结果待核实、收据和事件，并标注已人工核查。迟到的旧读取不能抹去已知核查；关闭/重开及只读重载不重复执行。核查失败保留原事实，仅允许明确重试核查；其他记录的晚到响应不覆盖当前窗口。清理首页不再把已核查的未知批次列入新的核查要求，原历史事实仍可查看。

只有已结束且含未知项目的清理批次、或 interrupted/uncertain 卸载记录可以核查。运行中、尚无可靠结果但 worker 仍在、已知成功/未开始/取消、错 ID/摘要、损坏快照、异常同步模式或退出中均不保存。RPC 仅接受两个固定模块、原请求 ID、快照摘要和明确确认，不接收修改路径或命令。

核查使用 SQLite IMMEDIATE/FULL 事务，读取并验证原完整详情/事件及快照，再新增一条绑定快照 SHA-256 的记录；重复提交保留第一次时间。客户端要求响应除 reviewedAt 外所有原事实不变，不能用核查响应把未知改成 moved。它只解除该份未知结果对共享准入的阻塞；其他未知、活动任务、容量、权限、保护和新计划当次检查仍有效。

## 数据库升级与损坏处理

schema v7 新增 execution_reviews / uninstall_reviews，分别以外键绑定原批次；不重写十张原设置/三类执行表。v1–v6 升级前先以 VACUUM INTO 保存包含已提交 WAL 的原库，再在单一事务中迁移；备份或迁移失败保留原库，未来版本拒绝打开。原 v6 备份的只读详情可继续读取，reviewedAt 为 null；旧 schema 不接受新核查写入。

新表同时检查核查时间的 SQLite 实际类型为 integer 且非负。另实际复现旧 maintenance_reviews 的 INTEGER affinity / CHECK(at>=0) 会接受文本时间，详情虽拒绝，旧准入查询仍可能误认已核查；三模块的准入现在均核对时间类型/范围和摘要。该受控损坏场景回归先失败再通过；既有维护读取和回收仍先验证完整记录，损坏不会变成成功或自动删掉证据。

清理、卸载的原未知/收据记录仍按原保留策略长期保留，核查标记不授权清除。共享 64 批/64 MiB 容量限制保持；达到上限的可操作归档/清除方案仍需完成，不能用人工核查假装容量已经释放。
