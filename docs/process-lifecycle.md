# 任务的进程所有权与退出边界

2026-10-16 初版覆盖目录分析、状态、应用列表、开发缓存、清理预览和规则复查。2026-10-20 新增受限日志执行后的共用退出控制器与隔离原生联验，见本文末节；未改变 clean/rules 协议或 SQLite v3。

## 主进程回收前完成信号操作

旧实现先 `child.wait()` 回收主进程，再用保存的数字 PID 清理进程组。主进程消失后该 PID/PGID 可能被复用，保存一个数字不足以证明后续信号仍属于原任务。

现在每次启动都建立独立进程组，注册由互斥锁保护的 PID 和本次独有的 lease。通过 macOS `waitid(WEXITED | WNOHANG | WNOWAIT)` 观察退出，保留未回收的主进程，直到最后一次进程组信号已经发出并注销注册，之后才调用 `child.wait()`。信号、注销及退出时的强制清理使用同一把锁；旧 lease 不能清除或停止后一次注册，即使数字 PID 相同。

这依赖当前运行器是该子进程的唯一回收者。无法确认未回收子进程所有权时返回错误并停止按 PID 发信号。没有根据命令行、名称、日志或历史 PID 搜索并停止其他进程，不枚举用户应用作为清理对象。

## 普通取消与超时

- 启动前已经取消则不创建进程；同一个 Job 不能同时注册第二个进程。
- 取消、任务超时、输出读取失败或超过 32 MiB 上限时，先向仍拥有的进程组发送 TERM，等待 3 秒，再在主进程回收前向该组发送 KILL。原有任务期限保持；停止阶段另有预算。
- Mole 的 Perl 超时助手会为它的命令另建进程组，并在收到 TERM 时清理它。直接 KILL 助手可能使它来不及处理子进程；TERM 宽限期改善这一场景，没有改变上游源码或默认超时后端。
- 等待调用方被强制中止时，作用域 guard 直接清理仍拥有的进程组，输出读取任务也会中止；这一回退没有异步宽限期。

普通取消完成前仍保留运行任务，前端已有“正在停止任务进程…”及规则复查取消状态继续适用；后端结束前不会接受同类任务。取消不提供重新执行或断点续删。

## 输出与回收不能无限等待

stdout/stderr 独立异步读取，各自保留 32 MiB 加一个检测字节。超过上限会启动停止流程，不等原任务期限耗尽。读取句柄离开作用域时中止，避免未来被中止后留下无限等待的读取任务。

主进程结束后，输出管道最多先等待 1 秒；仍有写入者则启动 TERM/KILL 停止流程，并明确作为失败。最后回收最多等待 1 秒，输出再收集最多 1 秒。回收或输出未完成时返回需要核实的错误，不报告成功。一般命令正常退出且输出已读完时直接完成，不额外等待 3 秒。

## 正常退出应用

收到退出请求时，在任务准入锁下停止接受新的检查与规则复查，取消已有任务，并暂缓真正退出。重复退出请求不重复启动停止流程，也不能提前越过它。

macOS 默认的原生 Quit selector（包括默认菜单的 ⌘Q）可能直接进入 `Exit`，绕过可延迟的 `ExitRequested`。这条路径在终止回调返回前进行同样有期限的等待，让独立异步运行时完成停止和历史写入；只有已经进入终止的主线程会在这里等待。不能只注册 `ExitRequested` 就认为覆盖了 macOS 正常退出。

最多等待 6 秒，让普通停止及历史写入完成；仍有任务时只强制停止当前注册的进程组，再结束应用。未能落盘的历史在下次启动仍按已有规则标为中断，不自动重放。该预算不证明所有系统调用或后台工作都已经完成，真实进程强杀、系统终止和断电不经过此路径。

## 验证与剩余边界

新增 6 组普通 Rust 测试使用自己创建的短期进程和临时文件，覆盖 WNOWAIT 重复观察与回收顺序、旧 lease 拒绝、预取消/重复注册、嵌套进程组 watchdog 完成回收、拒绝 TERM 后升级、等待方 abort、输出超限，以及脱离组的写入者不再阻塞返回。独立进程组反例使用有固定期限的只读 fixture，等待它自行结束，不用保存的 PID 强制清理。

另一个默认忽略的检查加载当前清单验证过的固定版 Mole `lib/core/timeout.sh`，显式选择其 Perl 后端，只运行独立临时 PID 标记与短期 sleep。普通取消后观察到该受控命令已结束；不运行 Mole 清理、不修改个人目标。运行方式：

```bash
node scripts/cargo.mjs test process::tests::pinned_mole_perl_timeout_cleanup_survives_normal_cancellation -- --ignored --exact --nocapture
```

本机原生 App 验证：扫描 `f082771c` 点击取消后先显示正在停止，再保存为已取消；扫描 `468724df` 通过 ⌘Q、`7127b15c` 通过关闭最后窗口，均在进程结束前写入已取消。重启后的历史保留终态，没有自动重启清理预览。首次只处理 `ExitRequested` 的版本曾让 `204f6a0d` 中断，原记录仍如实保留；补上原生终止回调的等待后，上述两条退出路径通过。

这里没有承诺任意后代进程都能清理：外部命令可脱离组、关闭输出句柄，或采用不同的超时后端；特别是 coreutils timeout 的所有者死亡语义与 Perl 不同。输出关闭也不能证明整个进程树为空。强制 abort、强杀 App、长时间挂起的内核调用、其他架构/系统及外部工具矩阵仍需验证。

这些进程管理机制不判断候选文件是否被应用、锁或后台服务使用；Mole 当前活动/不确定结果继续按原规则展示，也不提供文件执行许可。受限日志的独立确认、当次规则与对象验证另见 [日志执行](log-cleanup-execution.md)，不能由进程停止推导文件状态。

数据库的跨实例占用权已与 AppState/后台工作句柄共同保留；重复启动不能提前恢复运行记录，见 [实例占用](instance-ownership.md)。这不增加对清理目标或外部后代的锁保证。

## 共用退出期限与在途日志结果（2026-10-20）

`shutdown::Controller` 统一 `ExitRequested` 的异步等待与 Cocoa 直接 `Exit` 的同步等待。第一次退出在任务准入的 registry 锁内关闭新任务准入、请求取消现有任务并设置一次单调时间的 6 秒期限；重复请求不再建等待驱动，原生终止回调复用原期限，避免从另一入口再次追加 6 秒。

- registry 中的任务只有在真正完成结果收集、落盘和工作句柄释放后才消失；此前控制器保持 Waiting，不把取消请求当终态。
- 全部工作按现有活动状态结束后返回 Drained；超时只对当前注册并仍拥有的子进程组发强制信号一次，返回 TimedOut。后者是允许结束进程，不是证明所有工作完成。
- Foundation 的在途原生操作没有可强杀的子进程组，控制器不终止线程、不补写文件成功/失败、不移除工作句柄。进程在结果提交前结束时，原持久意图仍由启动对账保留待核实。
- registry/退出状态锁不跨工作等待、SQLite 或原生文件操作持有。所有后续任务准入继续拒绝，直到新进程初始化；不自动续删。

2026-10-24 补充：Quick Look 原生 supervisor 已接同一 Job 进程登记，退出超时的最后一轮强停不再遗漏维护子进程；最后信号/注销在回收前完成，登记冲突不影响原进程。新增受控子进程回归先复现未登记失败，再验证强停可达性、回收及登记撤下。具体边界见 [维护执行核心](maintenance-quicklook.md)；这不替代实际 App 的执行中退出/强杀验收。

三组普通测试验证：两个入口的请求共享首次期限、重复请求幂等、空闲退出/正常完成、超时不擦除无子进程的原生任务句柄，以及只强停注册的自建进程组且旧 lease 失效。时间判断用注入单调时刻确定验证，不靠睡眠放宽等待期限。

显式原生联验把同一控制器接入正式日志循环，在批次开始、意图后、原生返回后、单项提交后分别请求退出。四类情形均取消后续项；未开始时无移动，在途时首项真实收据仍提交，工作句柄移除前为 Waiting、移除后 Drained，安装准入在结果收集期间仍被持有。仅使用专用临时 HOME 文件与 fixture 正面规则；发生移动的文件均按确切收据核对并取回，原始与未选文件正文保持一致。

```bash
node scripts/cargo.mjs test --locked log_cleanup::tests::shutdown::native_exit_collects_inflight_result_and_cancels_later_items_before_drain -- --ignored --exact --nocapture
```

本轮 ad-hoc App 原生回归只运行真实 dry-run 预览：`471a8b15-9cd9-48b8-b44d-a93b1c18bf33` 在扫描中按 ⌘Q，`7b65cb8e-d839-4a87-b947-e63b429e36ec` 在扫描中关闭最后窗口；进程均结束，重启历史保持已取消，没有重新启动预览。它验证两个 App 入口接入共用控制器的只读回归；不是实际 App/TCC 身份下修改任务、系统 API 内部中止、断电、跨卷或休眠的完整验收。

## Darwin 的非终态 waitid 事件（2026-10-25）

实际维护子进程挂起验收揭示：本机 waitid 即使使用 WEXITED | WNOHANG | WNOWAIT，也会返回匹配 PID 的 CLD_STOPPED（5）。原先仅比较 PID 导致提前最终收集并杀掉尚未退出的命令。自建原生 C 探针与两个 Rust 回归先复现；清理/只读与维护共用的终态判断现在同时要求匹配 PID 和 CLD_EXITED、CLD_KILLED 或 CLD_DUMPED。停止、继续、陷阱或空事件均不当作完成，不回收/注销仍在运行的子进程；原期限、取消、租约和最终信号边界保持。实际修复前批次保留未知原因，不改写成已取消。
